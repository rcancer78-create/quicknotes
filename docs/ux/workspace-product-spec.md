# QuickNotes Workspace — продуктовое ТЗ

Статус: утверждённое направление интерфейса, 19 сентября 2026 года.

Связанные канонические документы: `VISION.md`, `ROADMAP.md`, `ARCHITECTURE.md`, `INVARIANTS.md`.

## 1. Решение

Главное окно QuickNotes становится единым большим рабочим пространством, визуально близким к OneNote по ощущению постоянного полноэкранного места для работы. Основная поверхность показывает карточки заметок и позволяет раскрыть выбранную заметку для чтения или редактирования, не покидая рабочее пространство.

Это изменение оболочки и навигации, а не формата данных:

- `Note.Title` и Markdown `Note.Text` остаются единственным каноническим содержимым заметки;
- существующие теги, поиск, история, защита, вложения, журнал черновика, импорт, экспорт и Sync не получают параллельной реализации;
- доска, список и фокусный редактор показывают одни и те же заметки через общие ViewModel и команды;
- отдельное компактное окно быстрого захвата сохраняется;
- текущая трёхпанельная компоновка сохраняется как режим «Список» до отдельного решения об удалении.

## 2. Пользовательская цель

Пользователь открывает QuickNotes на весь экран и видит не узкий список с постоянно занятым редактором, а единое поле знаний:

1. карточки дают обзор материала;
2. теги и сохранённые виды быстро меняют содержимое поля;
3. выбранная карточка раскрывается в том же окне;
4. быстрый захват из другого приложения добавляет карточку во «Входящие»;
5. пользователь всегда понимает, сохранена ли правка локально и требуется ли действие для Sync.

Целевой путь:

> поймал текст → увидел карточку в общем пространстве → раскрыл → дополнил → быстро нашёл снова.

## 3. Неизменяемые продуктовые границы

### 3.1. Обязательно сохранить

- local-first: создание, изменение и поиск не ждут сеть;
- текущую SQLite-схему заметки, пока конкретный этап не требует отдельно проверенной миграции;
- Markdown как канонический формат;
- заголовок, текст, источник, теги, вложения, историю и protected envelope;
- локальный commit отдельно от фонового Sync;
- журнал черновика и его защищённый вариант;
- корзину, восстановление и подтверждения разрушительных действий;
- быстрый захват, instant save и OCR;
- отдельное окно `NoteEditorWindow` для глобального захвата и `Ctrl+E`;
- существующие режимы Edit / Split / Preview;
- пагинацию и ограниченную материализацию карточек;
- доступность с клавиатуры и UI Automation.

### 3.2. Не входит в первую реализацию

- бесконечный canvas с произвольными X/Y-координатами;
- свободное наложение карточек и Z-order;
- рисование, рукописный ввод, PDF-аннотации;
- WebView2/WYSIWYG и HTML как основной формат;
- прямой импорт внутреннего формата OneNote;
- новый тип `Page`, дублирующий `Note`;
- отдельная task-модель;
- синхронизация положения каждой карточки между устройствами;
- удаление существующего режима «Список» до доказанной замены.

## 4. Информационная архитектура

Главное окно состоит из трёх постоянных уровней.

### 4.1. Верхняя панель

Содержит глобальный поиск, переключатель «Доска / Список», действия «Новая заметка» и «Снимок», компактное меню редких действий и доступный вход в полноэкранный режим. Высота панели не увеличивается относительно существующего chrome без измеренной причины.

### 4.2. Навигация

Сворачиваемая левая панель содержит виртуальные разделы, дерево тегов, сохранённые рабочие виды и явное действие создания тега.

Состояния панели:

- normal: полные подписи и счётчики;
- compact: короткая подпись/иконка с tooltip и доступным именем;
- hidden: только в полноэкранном focus-сценарии, с доступной командой возврата.

Ширина и состояние сохраняются в `AppSettings`. Некорректные значения безопасно ограничиваются.

### 4.3. Центральное рабочее пространство

Имеет три представления одного набора данных:

1. **Доска** — адаптивная сетка карточек.
2. **Список** — существующая трёхпанельная компоновка.
3. **Фокус** — выбранная заметка занимает основную область, рядом остаётся компактный контекстный список или полностью скрывается.

Переключение представления не сохраняет заметку само по себе, не создаёт ревизию и не инициирует Sync.

## 5. Доска карточек

### 5.1. Сетка

- число колонок вычисляется из доступной ширины;
- целевая ширина карточки: 260–380 DIP;
- при узкой ширине используется одна колонка либо существующий master/detail;
- карточки виртуализируются или загружаются страницами;
- первая страница появляется без материализации всего результата;
- порядок использует существующие сортировки;
- закреплённые заметки остаются первыми при соответствующей сортировке;
- плотность normal/compact меняет только представление.

### 5.2. Содержимое карточки

Первый уровень показывает заголовок, ограниченный preview, один-два информативных тега, избранное/закрепление и публикационный статус только для PendingUpload, Syncing, Conflict или Error.

Постоянно не показываются локальный ID, полный набор технических метаданных, успешный cloud-статус на каждой карточке, plaintext защищённой заметки и все действия одновременно.

### 5.3. Жесты

- один клик: выбрать;
- `Enter`: раскрыть в режиме «Фокус»;
- `Space`: развернуть preview, если это не конфликтует с accessibility;
- `Ctrl+E`: открыть существующее отдельное окно;
- `Esc`: вернуться из «Фокуса» на доску;
- контекстное меню: существующие безопасные действия;
- скрытый двойной клик не является обязательным путём.

Навигация при незавершённой правке следует единому контракту встроенного редактора: commit, сохранённый journal либо явный диалог. Тихая потеря или подавленный commit-error запрещены.

## 6. Фокус и редактирование

Фокусный режим использует существующий `NoteEditorViewModel` и сервисы. Запрещено создавать второй редактор с отдельной логикой commit, protection, tags, attachments или draft journal.

- заголовок и основные действия остаются видимыми;
- текстовая колонка ограничивается для читаемости;
- Edit / Split / Preview сохраняются;
- outline появляется только для структурированной заметки;
- список соседних карточек можно свернуть;
- `F11` убирает несущественный chrome, но оставляет выход и статус сохранения.

Пользователь различает сохранённую локальную версию, несохранённый editor draft, journal, pending Sync, конфликт и ошибку commit. Их нельзя сводить к одному индикатору «Сохранено».

## 7. Рабочие пространства и сохранённые виды

### 7.1. Первый релиз

«Рабочее пространство» — сохранённый запрос представления, а не контейнер заметок. Оно содержит имя, виртуальный раздел, включённые/исключённые теги, поисковую строку, сортировку, режим Доска/Список и плотность. Заметка не копируется и может появляться в нескольких видах.

### 7.2. Хранение

До отдельного ADR сохранённые виды являются локальными UI-настройками. Они не входят в note revisions и не создают Sync-пакеты. Перенос между устройствами требует отдельного формата и конфликтной модели.

### 7.3. Ручной порядок

Ручной порядок не входит в первый релиз. До его добавления нужно определить область порядка, Sync, объединение конкурентных изменений, место новых карточек и поведение при удалении тега/вида.

## 8. Полноэкранный режим

- команда по умолчанию: `F11`;
- повторный `F11` и контекстный `Esc` возвращают предыдущее состояние;
- границы окна восстанавливаются точно;
- используется текущий монитор;
- системная рамка скрывается только на время режима;
- критичные статусы и выход доступны с клавиатуры;
- аварийное завершение не оставляет повреждённый `WindowState`;
- действующий tray-contract сохраняется.

## 9. Поиск и фильтрация

- источник результата остаётся FTS5 + структурные операторы;
- быстрый ввод отменяет устаревший запрос;
- Доска показывает тот же детерминированный результат, что Список;
- нулевой результат отличается от пустой базы/раздела и предлагает сброс фильтра;
- закрытые protected notes не раскрываются;
- highlighting не должен заметно снижать прокрутку.

## 10. Быстрый захват

- глобальные hotkey и tray-действия сохраняются;
- компактное окно не заменяется workspace;
- instant save добавляет карточку во «Входящие» после local commit;
- открытый draft отображается согласно journal/commit-контракту;
- OCR создаёт обычный draft;
- новая карточка не перехватывает ввод из стороннего приложения.

## 11. Производительность

- не более 50 materialized ViewModel на первой странице;
- поиск сохраняет p95 ≤ 150 мс на 10 000 заметок;
- память в покое остаётся ≤ 400 МБ;
- Доска/Список не перечитывает всю базу;
- полный Markdown всех карточек не рендерится синхронно;
- раскрытый preview не отключает виртуализацию всей коллекции;
- этапы W2–W3 повторяют baseline-измерения.

## 12. Accessibility и клавиатура

- карточки представлены доступной сеткой/списком;
- выбранность и раскрытие объявляются UI Automation;
- Tab не проходит через декоративные метки;
- стрелки перемещают выбор предсказуемо;
- `Enter`, `Ctrl+E`, `Esc`, `F6`, `F11` документированы в `ShortcutCatalog`;
- focus ring видим в обеих темах и High Contrast;
- Narrator/NVDA не читает plaintext заблокированной заметки;
- поддерживаются DPI 100/125/150/200% и длинные русские строки.

## 13. Безопасность и сохранность

- layout не содержит protected plaintext;
- заголовок/preview protected note не кэшируются в настройках;
- screenshot-smoke использует синтетические данные и isolated profile;
- переход режима не очищает journal до успешного commit;
- повреждённые layout settings восстанавливаются безопасно;
- удаление вида не удаляет заметки;
- удаление карточки использует существующую корзину;
- Sync/crypto/archive не меняются вместе с оболочкой workspace.

## 14. Архитектурный план

Предпочтительные границы:

- `WorkspaceViewMode`: Board, List, Focus;
- `WorkspaceLayoutState`: UI-состояние и безопасные размеры;
- `SavedWorkspaceView`: локальный сериализуемый фильтр;
- `WorkspaceViewModel`: координация вида, paging и переходов;
- существующий `NoteCardViewModel`: источник карточки;
- существующий `NoteEditorViewModel`: единственный редактор;
- существующий `SearchService`: единственный источник результата;
- `WorkspaceLayoutHelper`: чистые функции адаптивной компоновки и clamping.

`MainViewModel` не получает второй набор сохранения. При росте координации workspace выделяется через typed bundle/явную зависимость согласно ADR-013, без DI-контейнера.

## 15. Пошаговая реализация

### W0. Спецификация и baseline

- [x] Зафиксировать продуктовую модель этим документом.
- [ ] Сохранить эталонные кадры текущего трёхпанельного режима.
- [ ] Зафиксировать keyboard map, размеры, DPI и performance baseline.
- [ ] Начинать implementation только с чистого worktree.

### W1. Оболочка и переключение

- добавить `WorkspaceViewMode` и переключатель Доска/Список;
- сохранить режим и состояние навигации;
- режим «Список» оставить функционально эквивалентным baseline;
- добавить пустую Board-поверхность за feature gate;
- не менять Note/схему/Sync.

Выход: переключение обратимо, перезапуск восстанавливает режим, Список не регрессировал.

### W2. Read-only доска

- вывести существующие карточки адаптивной сеткой;
- сохранить paging, поиск, разделы, теги и сортировку;
- реализовать выбор, контекстное меню, pin/favorite и `Ctrl+E`;
- сохранить neutral protected presentation;
- добавить light/dark × wide/narrow screenshot smoke.

Выход: Доска и Список совпадают по IDs/порядку; полный корпус не материализуется.

### W3. Фокусный режим

- раскрыть карточку в существующий редактор;
- реализовать единый переход назад с journal/commit/error-contract;
- сохранить Edit/Split/Preview, outline, attachments, history, protection и tags;
- покрыть Board ↔ Focus ↔ List race/regression-тестами.

Выход: нет тихой потери draft, двойного commit, лишней revision или Sync enqueue.

### W4. Полноэкранная работа

- добавить `F11`, восстановление окна и monitor-aware поведение;
- сворачивание навигации и контекстного списка;
- сохранить tray/close contract;
- выполнить ручную multi-monitor/DPI проверку.

Выход: безопасное восстановление окна; критичные действия доступны без мыши.

### W5. Сохранённые виды

- локальная модель фильтра;
- создание, переименование, применение и удаление;
- удаление вида не затрагивает заметки;
- неизвестные/старые поля fail-safe;
- экспорт/Sync views не добавлять.

Выход: один набор заметок появляется в разных видах без копирования или revisions.

### W6. Полировка и решение о default

- полная visual/accessibility/performance матрица;
- минимум неделя реального использования Доски и Списка;
- зафиксировать наблюдаемые проблемы;
- только затем решить, становится ли Доска default;
- удаление Списка требует отдельного решения и rollback UX.

## 16. Проверка каждого этапа

1. Whitespace-gate затронутых C# и общий gate после устранения baseline-нарушений.
2. Release build с warnings as errors.
3. Focused-тесты.
4. Полный Release suite с hang timeout перед commit этапа.
5. `git diff --check`.
6. Isolated-profile screenshot smoke без cloud credentials.
7. Light/dark, wide/narrow, DPI 100/125/150/200%, клавиатура.
8. Protected note без plaintext-утечки.
9. Draft/commit/navigation failure injection.
10. Performance baseline для W2–W3.

## 17. Пользовательские сценарии приёмки

1. Из полноэкранной доски пользователь создаёт заметку и сразу видит карточку.
2. Instant save из Notepad создаёт Inbox-карточку без перехвата фокуса.
3. Поиск даёт одинаковые заметки в Доске и Списке.
4. Ветка тегов перестраивает доску без загрузки корпуса.
5. Protected note не раскрывается в карточке, tooltip или UI Automation.
6. Правка переживает Board → Focus → List и crash recovery по journal-contract.
7. Ошибка commit видима; draft сохранён, ложного «Сохранено» нет.
8. Pending Sync не блокирует локальную работу.
9. Удаление сохранённого вида не удаляет заметки.
10. Повреждённые layout settings дают безопасную компоновку.

## 18. Rollback

Каждый этап сохраняет рабочий режим «Список». До W6 rollback отключает Board/Focus и читает те же заметки существующим интерфейсом. W1–W4 не требуют миграции пользовательских данных. Локальные настройки видов W5 необязательны и игнорируются старой версией без потери заметок.

## 19. Организация внешней реализации

- один внешний исполнитель получает один этап W1–W6;
- в одном checkout одновременно работает не более одного пишущего исполнителя;
- brief фиксирует scope, запрет commit/destructive Git/secrets/live profile/cloud и acceptance-команды;
- Codex независимо проверяет diff, тесты, runtime/UI и документацию;
- замечания передаются одним correction batch в новую сессию;
- этап фиксируется отдельным commit только после независимой приёмки.
